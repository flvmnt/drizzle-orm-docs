<Prerequisites>

- Get started with [PostgreSQL](/docs/get-started-postgresql)
- [Drizzle Kit](/docs/kit-overview)
- Node.js 20 or later

</Prerequisites>

`drizzle-kit generate` produces SQL migration files. For PostgreSQL projects, [pgfence](https://pgfence.com) can analyze those files before deployment and report lock modes, known migration risks, coverage, and safer alternatives where available.

Static analysis is one part of a migration review. A report with no findings does not prove that a migration is safe for your database, traffic, or deployment process.

## Install pgfence

<Npm>@flvmnt/pgfence@0.8.1 -D</Npm>

## Generate, analyze, review

<Steps>

#### Generate a migration

```bash copy
npx drizzle-kit generate
```

The commands below assume that your configured output directory is `drizzle/` and its migration SQL files are directly inside that directory. Adjust the paths for your configuration.

#### Analyze the generated SQL

```bash copy
npx --yes @flvmnt/pgfence@0.8.1 analyze --format drizzle drizzle/*.sql
```

pgfence reads the generated SQL, including Drizzle's statement-breakpoint comments. It reports known lock and rewrite risks and policy checks such as missing `lock_timeout`. Review the coverage summary and any unsupported statements as well as the findings. Coverage describes what pgfence processed against its supported patterns; it does not certify that every possible database risk was checked.

For example, a generated index statement such as this blocks writes while the index is built:

```sql
CREATE INDEX "users_name_idx" ON "users" USING btree ("name");
```

pgfence reports a `SHARE` lock and `MEDIUM` risk for this statement, with a concurrent-index alternative where applicable.

#### Review and plan deployment

Review suggested changes, PostgreSQL version assumptions, table sizes, and application compatibility. Test the migration using the same runner and transaction behavior as production before applying it.

</Steps>

<Callout type="warning" title="Migration runner transactions">
  `CREATE INDEX CONCURRENTLY` cannot run inside a transaction. A SQL file alone
  does not show transactions started by Drizzle's migration runner. pgfence can
  detect explicit SQL transaction statements, but it cannot certify the runner's
  behavior from generated SQL. Check the runner you use and execute concurrent
  operations separately when it wraps migrations in a transaction.
</Callout>

## Check migrations in CI

This example analyzes SQL files in the same `drizzle/` directory when a pull request changes that directory. It runs static analysis without a database connection or database credentials.

```yaml copy
name: Migration safety check

on:
  pull_request:
    paths:
      - "drizzle/**"

jobs:
  pgfence:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - name: Analyze migrations
        run: npx --yes @flvmnt/pgfence@0.8.1 analyze --format drizzle --ci --max-risk low --unknown block drizzle/*.sql
```

`--max-risk low` allows findings up to `LOW` risk and fails on `MEDIUM`, `HIGH`, or `CRITICAL` findings. Policy errors also fail the check. `--unknown block` fails when pgfence reports an unanalyzable statement. Unreadable inputs also fail the command.

The example analyzes all matching migration files, including older ones. Review the existing migration history when introducing the check. If you store SQL in subdirectories, use an explicitly recursive file selection and verify that every intended migration is included; the shell glob above covers only `drizzle/*.sql`.
